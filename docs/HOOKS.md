# 워크플로 훅 — 검토서를 저장하는 순간 인용을 검증한다

`fin_verify`는 물어봐야 답한다. 물어보는 것을 잊으면 검증은 일어나지 않는다.
Claude Code 훅으로 걸면 **검토서(.md)를 저장할 때마다** 인용이 자동으로 대조되고,
실존하지 않는 조문이 있으면 Claude가 그 사실을 즉시 통보받는다.

---

## 1. 검증 스크립트

`scripts/verify-file.mjs`가 파일 경로를 받아 그 안의 법령 인용을 `fin_verify`로 대조한다.

```bash
node scripts/verify-file.mjs 검토서.md
```

```
[인용 검증] 검토서.md — 인용 3건
  ✓2 / ✗1 / ⚠0

✗ 실존하지 않는 인용 1건 — 이 문서는 그대로 쓰면 안 됩니다
  ✗ 법인세법 제9999조 — 법령 「법인세법」은 실존하나 제9999조가 없음 (정상 조회 후 0건). 조문 번호 확인

해당 인용을 수정하거나 삭제한 뒤 다시 저장하세요.
```

동작 규칙:

- **✗이 1건이라도 있으면 실패** (기본 종료 코드 1). ✗은 "정상 조회 후 0건"일 때만 나온다 — 그래서 조회 대상 DB에 없는 종류의 문서에는 ✗를 쓰지 않는다
- **삭제된 조문은 ✓가 아니라 ⚠ "사용 보류"다.** 법제처는 삭제된 조문도 번호를 남긴다(`제39조 삭제 <2001.12.31>`). 번호가 있다고 ✓를 주면 삭제된 조문이 "실존"으로 통과하므로, 조 전체가 삭제된 자리표시면 사용 보류로 보고하고 `WARN_EXIT`로 나간다. 항·호 하나만 삭제된 조문은 살아 있는 조문이다. 삭제 전 규정을 인용한 문서라면 `FIN_VERIFY_BASIS_DATE`로 그 시점을 지정하면 그 시점 본문으로 판정한다
- **국세청 기본통칙·「○○세(법)집행기준」은 ⚠다.** 법제처 행정규칙 DB에는 이름에 "통칙"이 든 규칙이 한 건도 없다(2026-09-16 실측) — 0건이 부존재의 증거가 아니므로 번호 실존은 검증하지 않고 모법(예: 법인세법)의 실존만 확인해 ⚠로 보고한다. 이 ⚠는 인용이 틀렸다는 뜻도, 쓰면 안 된다는 뜻도 아니다 — **원문 대조가 필요하다**는 뜻이다. 기본통칙을 인용한 문서는 `WARN_EXIT`로 끝나니 국세법령정보시스템에서 원문을 확인하라(모법까지 확인되지 않으면 사용 보류로 올라간다). 집행기준은 **먼저 행정규칙 DB에서 정확 일치를 찾고**, 있으면(예: 「(계약예규)정부 입찰ㆍ계약 집행기준」) 일반 행정규칙으로 정상 대조한다. 고시·훈령·예규는 종전대로 DB에 없으면 ✗다
- **`FIN_VERIFY_BASIS_DATE`는 조문까지 인용한 법령에만 적용된다.** 조문 인용은 기준일에 시행 중이던 판본을 찾아 그 본문으로 대조한다. 행정규칙(고시·훈령·규정 등)은 연혁 본문 대조를 하지 않아 현행 본문으로 판정하고, 조문 없이 법령명만 인용한 것(「법인세법」)은 판본을 조회하지 않는다 — 둘 다 판정 줄에 `[현행 기준 대조 — 기준일 미적용]`을 붙여 ✓·✗ 대신 ⚠로 보고한다 (현행·연혁 DB 어디에도 없는 규칙의 ✗만 유지)
- **⚠는 ✗와 다르게 취급하되, "통과"로 삼키지도 않는다.** ⚠의 공통점은 "없음(✗ — 정상 조회 후 0건)이 아니다"라는 것뿐이고 사유는 판정 줄마다 다르다 — 어느 쪽이든 `FAIL_EXIT`가 아니라 `FIN_VERIFY_WARN_EXIT`(기본 1, 비차단)로 나간다(✗와 섞이면 아래 최댓값 규칙). 종전에는 일반 ⚠·⌛(연혁 추정)가 종료 코드 0이었는데, 그러면 검증이 하나도 안 된 문서(전 인용 타임아웃)가 "통과"로 읽힌다 (Codex 4차 차단 — 0의 stderr는 디버그 로그에만 남는다). 사유는 네 갈래다
  - **확인된 삭제** — 대조한 본문에 조 전체가 삭제된 자리표시만 있다. 대조한 본문은 기준일이 없으면 현행본, `FIN_VERIFY_BASIS_DATE`를 주면 그 시점 시행본, 행정규칙이면 현행 본문이다 — 그래서 "현행에서 삭제"라고 단정하지 않는다. 조회는 정상이었으므로 확인 실패가 아니다. `fin_verify`는 별도 헤더(`⚠️ 삭제된 조문 인용 있음 — 대조한 본문에서 삭제 확인(대조 시점은 판정 줄 참조)…`)를 띄우고, 훅은 사용 보류로 분류한다
  - **원문 대조 필요** — 국세청 기본통칙·집행기준(법제처 DB 미수록). 조회는 정상이지만 번호를 대조할 DB가 없다. 인용이 틀렸다는 뜻이 아니다
  - **미지원 범위** — 기준일을 줬지만 행정규칙이거나 법령명만 인용한 것(`[현행 기준 대조 — 기준일 미적용]`), 현행 DB에 없는 연혁 법령. 그 시점을 조회하지 않았으니 ✓·✗ 어느 쪽도 쓸 수 없다. 조문까지 인용한 법령은 기준일 시행본으로 대조하므로 여기에 들지 않는다
  - **조회 실패** — 조회 장애·타임아웃·분당 한도·전체 시간 상한·미검증 잔여. 장애를 근거 삭제 지시로 바꾸면 안 되므로 재시도하거나 원문으로 확인한다
  - `fin_verify`는 삭제가 아닌 ⚠가 하나라도 있으면 헤더에 `※ ⚠는 "없음"(부존재 확정)이 아닙니다 — 사유가 줄마다 다릅니다(…)` 고지를 붙인다 — 기본통칙만 있어도 붙는다. 삭제 조문만 있을 때는 붙이지 않는다
- **⚠ 중 "사용 보류"와 미검증 잔여는 따로 다시 보고한다** (stderr. stdout의 ⚠ 목록도 같은 기준으로 `사용 보류 N건`과 `판정 불가 N건`을 나눠 적어 두 출력의 건수가 같다). 사용 보류는 판정 줄에 "사용 보류"가 적힌 ⚠다 — 미등재 약칭·환각 의심, 사내 문서일 수 있는 규정, 줄바꿈으로 끊긴 법령명, 모법이 확인되지 않은 기본통칙, 삭제된 조문. 사유 확인 전까지 쓰면 안 되는 인용이라, 다른 ⚠와 뭉뚱그리면 마지막 줄의 "인용 검증 통과"가 그것까지 통과시킨 것으로 읽힌다. 나머지 ⚠는 `판정 불가`로 묶어 보고하는데, 여기에는 조회 실패뿐 아니라 DB 미수록·기준일 미적용처럼 조회가 정상이었던 ⚠도 들어간다 — 줄마다 적힌 사유를 따른다. `FIN_VERIFY_WARN_EXIT` 기본 1(비차단 오류)이면 대화 기록에 `hook error` + stderr 첫 줄이 표시되고, `2`로 올리면 전문이 Claude에게 전달된다
- **✗와 ⚠가 섞이면 해당 종료 코드의 최댓값으로 나간다** — `FAIL_EXIT=0`(경고만 모드)에 `WARN_EXIT=2`를 함께 두어도 보류 보고가 ✗의 exit 0에 가려지지 않는다
- **추출 0건은 두 갈래다.** 조문 번호·법령 표기의 흔적조차 없으면 그냥 통과한다 (검증할 것이 없다). 흔적은 있는데 추출이 0건이면 `WARN_EXIT`로 나가며 `⚠ 인용 표기 흔적은 있으나 추출 0건`을 보고한다 — 마크다운 목록 표시와 줄바꿈으로 법령명이 갈라지면(`- 국가를 당사자로 하는 계약에 관한` + 줄바꿈 + `법률 제7조`) 추출이 0건이 되는데, 이것을 "인용 없음"과 함께 exit 0으로 보내면 실제 인용이 있는 검토서가 검증 성공으로 통과한다 (Codex 8차 차단)
- `.md`·`.txt`가 아니면 건너뛴다 (종료 코드 0)
- 인용이 15건을 넘으면 문단 단위로 나눠 여러 번 검증한다. `fin_verify`의 인용 상한(15건)을 그냥 넘기면 뒷부분이 조용히 미검증으로 남기 때문이다. 판정 수와 맞대는 검증 대상 수는 **나눈 구간마다 `fin_verify`가 보는 그대로** 센다 — 같은 구간 안에서 반복된 인용은 한 번만 판정되므로 한 번만 센다 (문단별로 세면 반복 인용 때문에 "미검증"이 거짓으로 나왔다). 한 문단의 인용이 15건을 넘어 잘린 경우는 그대로 미검증으로 보고한다
- 경로는 인자로도 받고, 훅이 stdin으로 주는 JSON(`tool_input.file_path`)에서도 읽는다

환경변수:

| 변수 | 뜻 |
| --- | --- |
| `LAW_OC` | (필수) 법제처 OPEN API 키. 저장소 `.env`에서 자동 로드된다 |
| `FIN_VERIFY_FAIL_EXIT` | ✗ 발견 시 종료 코드 (기본 `1`). **훅으로 쓸 때는 `2`** — 아래 3절 참고 |
| `FIN_VERIFY_WARN_EXIT` | 사용 보류·미검증 잔여·판정 불가(⚠·⌛)·추출 0건인데 표기 흔적 있음 시 종료 코드 (기본 `1` — 비차단 오류로 표시. `FAIL_EXIT=0`이면 기본 `0` = 전면 경고만 모드). **보류 상세까지 Claude에게 전달하려면 훅에서는 `2` 권장**. ⚠ `FAIL_EXIT=0`만 설정하면 API 장애·보류까지 exit 0이 된다 — ✗만 완화하려는 것이면 `WARN_EXIT`를 명시적으로 함께 설정하라 |
| `FIN_VERIFY_BASIS_DATE` | 기준일 `YYYY-MM-DD`. 과거 시점 기준으로 검토서를 쓸 때 (법령 조문에만 적용 — 행정규칙은 현행 대조를 ⚠로 표시). 달력에 있는 날짜여야 한다 — `2024-02-30` 같은 값은 `fin_verify`가 입력을 거절해 판정이 나오지 않는다 |
| `FIN_VERIFY_INTERVAL_MS` | 구간 간 간격 (기본 3000). 법제처 분당 한도 회피용 |

종료 코드 변수(`FIN_VERIFY_FAIL_EXIT`·`FIN_VERIFY_WARN_EXIT`)는 **0~255 정수만** 받는다. 빈 값(`""`)·공백·숫자가 아닌 값·범위 밖 값은 설정하지 않은 것으로 보고 기본값을 쓴다 — 설정 파일에서 값을 비워 둔 `FIN_VERIFY_FAIL_EXIT=""`가 0(경고만 모드)으로 해석돼 ✗ 문서가 exit 0으로 통과하던 문제가 있었다. 경고만 모드는 `"0"`을 명시해야 한다.

## 2. 훅 설정

`~/.claude/settings.json`(전체 프로젝트) 또는 프로젝트의 `.claude/settings.json`에 넣는다.

```json
{
  "env": {
    "FIN_VERIFY_FAIL_EXIT": "2",
    "FIN_VERIFY_WARN_EXIT": "2"
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "node /절대경로/fin-law-mcp/scripts/verify-file.mjs",
            "timeout": 180
          }
        ]
      }
    ]
  }
}
```

- `matcher`는 **도구 이름**에 대한 정규식이고 대소문자를 구분한다. 여러 도구는 `|`로 잇는다
  (`,` 구분자는 Claude Code v2.1.191 이상에서만 동작하니 `|`를 쓰는 편이 안전하다).
  `matcher` 값에 배열을 넣으면 스키마 오류로 **그 파일의 훅 전체가 무시된다**
- `timeout`은 **초** 단위다 (생략 시 600). 인용이 많은 문서는 구간을 나눠 여러 번 호출하므로 넉넉히 준다
- 훅은 stdin으로 `tool_name`·`tool_input`·`tool_response`·`cwd`·`session_id` 등이 담긴 JSON을 받는다.
  `verify-file.mjs`는 여기서 `tool_input.file_path`를 읽는다
- `.md` 필터는 스크립트가 직접 한다 (`matcher`는 도구 이름만 보고 파일 확장자는 못 본다).
  다른 확장자면 조용히 통과한다

### 왜 종료 코드 2인가

PostToolUse에서 종료 코드마다 결과가 다르다.

| 종료 코드 | 결과 |
| --- | --- |
| `0` | 성공. **stderr는 디버그 로그에만 남고 Claude에게 보이지 않는다** |
| `2` | stderr가 **Claude에게 전달된다.** 도구는 이미 실행됐으므로 되돌리지는 못한다 |
| 그 외 | 비차단 오류. 대화 기록에 `hook error` + stderr 첫 줄이 표시된다 |

즉 **✗ 결과가 Claude에게 닿게 하려면 종료 코드가 2여야 한다.** 그래서 위 설정의
`env`에 `FIN_VERIFY_FAIL_EXIT=2`를 둔다. Claude는 "이 파일에 실존하지 않는 인용이 있다"는
stderr를 읽고 스스로 고칠 수 있다. `FIN_VERIFY_WARN_EXIT=2`도 함께 두는 이유가 같다 —
기본값 1(비차단)이면 사용 보류 상세가 stderr에 있어도 Claude에게는 첫 줄만 보인다.

`VAR=값 node …` 같은 인라인 접두사 대신 `env` 키를 쓰는 이유는 이식성이다. 셸 형식 훅은
Windows에서 Git Bash가 있으면 Git Bash로, 없으면 PowerShell로 실행되는데
`VAR=값 명령` 문법은 PowerShell에서 동작하지 않는다. `env` 키는 셸과 무관하게 적용된다.
(훅에 `"shell": "bash"`를 명시해 고정하는 방법도 있다.)

### 종료 코드 3 — 실행 불가

키가 없거나(`LAW_OC` 미설정) `build/`가 없으면 스크립트는 **3을 반환하고 그 사유를 말한다**.
조용히 통과시키지 않는다 — "검증했다"고 믿는데 실제로는 아무것도 안 한 상태가
검증 실패보다 위험하기 때문이다. 대화 기록에 `hook error`가 뜨면 `.env`와 `npm run build`를 확인하라.

## 3. 범위 좁히기

모든 `.md` 저장에 API를 호출하는 것이 부담이면 경로로 좁힌다. 스크립트를 감싸는 대신
검토서를 특정 폴더(예: `검토서/`)에 모으고, 그 경로만 통과시키는 얇은 래퍼를 쓴다.

```bash
#!/usr/bin/env bash
# scripts/verify-if-review.sh
payload=$(cat)
path=$(echo "$payload" | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{try{console.log(JSON.parse(s)?.tool_input?.file_path||"")}catch{console.log("")}})')
case "$path" in
  *검토서/*.md|*reviews/*.md) echo "$payload" | node /c/dev/fin-law-mcp/scripts/verify-file.mjs ;;
  *) exit 0 ;;
esac
```

## 4. 설정이 먹었는지 확인

- `/hooks` — 설정된 훅을 이벤트별로 보여주는 읽기 전용 목록. **어느 설정 파일에서 왔는지**까지 보인다
- `claude doctor` — 설정 파일 검증. `matcher`에 배열을 넣어 훅 전체가 무시되는 것 같은 실수를 잡아준다
- `claude --debug` — 세션을 이 플래그로 켠 뒤 `.md`를 저장하면, 어떤 matcher가 검사됐고 훅이 어떤
  종료 코드·출력을 냈는지 디버그 로그에 남는다

설정 파일은 저장 후 잠시 뒤 실행 중인 세션에 자동 반영된다 (재시작 불필요).
우선순위는 `.claude/settings.local.json` > `.claude/settings.json` > `~/.claude/settings.json` 순이다.

## 5. 한계 — 훅이 해주지 않는 것

- **인용의 실존만 본다.** "법인세법 제26조가 실존하는가"는 확인하지만
  "그 조문이 이 사안에 맞는 근거인가"는 확인하지 않는다. 판단은 여전히 사람 몫이다
- **⚠는 차단하지 않는다.** 법제처 장애·분당 한도로 확인이 안 된 인용도, 삭제된 조문처럼
  **조회는 됐지만 그대로 쓰면 안 되는** 인용도, 기본통칙처럼 **원문 대조가 필요한** 인용도
  경고 종료(`WARN_EXIT`, 기본 1 = 비차단)로 남는다 —
  "통과"는 아니지만 자동으로 막지도 않으므로 stderr를 사람이 읽어야 한다. 장애성 경고가 반복되면
  `FIN_VERIFY_INTERVAL_MS`를 늘리거나 나눠서 재검증한다. 삭제 조문 경고는 인용을 고쳐야 사라지고,
  기본통칙·집행기준 경고는 인용이 맞아도 남는다(원문을 확인한 뒤 사람이 판단한다).
  훅으로 쓸 때 `FIN_VERIFY_WARN_EXIT=2`를 권하는 이유가 이것이다 (상세가 Claude에게 전달된다)
- **매 저장마다 실 API를 호출한다.** 법제처 분당 한도(30회)를 다른 도구와 공유하고 있다면
  3절처럼 경로를 좁히는 편이 낫다
- **한 구간 안에서도 분당 한도에 걸릴 수 있다.** 인용 하나에 법제처 조회가 여러 번 필요해,
  서로 다른 법령을 가리키는 인용이 한 구간(최대 15건)에 많으면 이 프로세스의 분당 한도
  (`FIN_DRF_RATE_PER_MIN`, 기본 30회)를 넘겨 뒤쪽 인용이 ⚠(분당 호출 한도 초과)로 남는다 —
  서로 다른 법령 20건을 넣은 `fin_verify` 테스트 입력에서는 11번째 인용부터 그렇게 됐다.
  `FIN_VERIFY_INTERVAL_MS`는 구간 사이 간격이라 한 구간 안의 조회는 나누지 못한다. 잠시 뒤 다시 저장해 재검증한다
- **되돌리지 못한다.** PostToolUse는 파일이 이미 쓰인 뒤에 돈다. 훅은 잘못된 인용이
  들어가는 것을 막는 게 아니라, 들어간 사실을 즉시 드러내는 장치다
