# fin-law-mcp

**재무·회계·세무·자금 실무 특화 한국 법령 MCP 서버.**
세무 질문의 근거가 되는 **조문·위임 조문·예규 후보를 법령명+조문으로 한 번에 모아 주고**,
인용한 조문이 실존하는지·삭제됐는지·어디까지 조회하지 못했는지를 **표시하는** 도구입니다.

AI가 답에 문서번호와 조문 원문을 붙일 재료를 주지만, **답변이 원문과 일치함을 보장하지는 않습니다.**
조회한 원문을 어떻게 읽고 무엇을 결론으로 쓰는지는 AI와 사람의 몫입니다 — 자세한 구분은 [하는 것 / 하지 않는 것](#이-도구가-하는-것--하지-않는-것).

## 예를 들면

> **"직원 결혼 축의금을 회사 돈으로 주면 세금 문제 있나?"**

이 서버가 있으면 AI는 기억 대신 조문 원문을 조회해 보고 답할 수 있습니다.
다만 AI가 **매번 조회한다는 보장은 없고**, 조회하지 않고 쓴 문장에는 이 서버의 표시도 붙지 않습니다.

AI가 질문에서 쟁점(여기서는 임직원 경조사비)과 근거 법령을 짚으면, 이 서버로 예규 후보와 조문 원문을 가져옵니다.

**① 예규 후보를 찾습니다** (적용 관계는 미확인 — 제목을 보고 사안에 맞는 것만 쓰세요) — `fin_ruling_search(query="경조사비", domains=["nts"])`

```text
■ 국세청 예규 [행정해석 — 과세실무 기준이나 법원 구속력 없음] — 최신순 4건
  · 서면법규과-691 (2013.06.17) 경조사비를 고객명의의 기부금으로 대납한 경우 기타소득 해당여부 · https://taxlaw.nts.go.kr/qt/USEQTA002P.do?ntstDcmId=010000000000151297
  · 서이46012-11058 (2003.05.27) 임직원에게 지급하는 경조사비의 손금산입 범위 · https://taxlaw.nts.go.kr/qt/USEQTA002P.do?ntstDcmId=010000000000004713
  · 법인46012-1801 (2000.08.22) 법인의 1회 거래처 경조사비지출액이 5만원이상인 경우 손금인정방법 · https://taxlaw.nts.go.kr/qt/USEQTA002P.do?ntstDcmId=010000000000058138
  · 법인46012-296 (1999.01.23) 사용인에게 지급하는 경조사비 등은 지출증빙서류 수취대상이 아님 · https://taxlaw.nts.go.kr/qt/USEQTA002P.do?ntstDcmId=010000000000505200
```

> 위 블록은 **2026-09-24 실측 발췌**(도메인 줄 + 항목 4줄)입니다. 이날 검색 총건수(`totalCnt`)가 4건이라 이 4건이 "경조사비" 검색 결과 **전부**였고, 전부 받았으므로 도메인 줄에 `· 검색 M건 중 …` 꼬리가 붙지 않았습니다. 항목 4줄은 2026-09-05 실측과 글자 단위로 같았습니다. 검색 결과는 법제처 데이터에 따라 바뀝니다.
> 결과가 표시 건수보다 많거나 정렬을 확인하지 못하면 도메인 줄이 달라집니다. 아래는 그 경우의 **형식 예시**입니다(실측 아님 — N·M·R은 응답마다 다릅니다).
>
> ```text
> ■ 국세청 예규 [행정해석 — 과세실무 기준이나 법원 구속력 없음] — 최신순 N건 · 검색 M건 중 최신 N건 표시
> ■ 국세청 예규 [행정해석 — 과세실무 기준이나 법원 구속력 없음] — 일자순 N건 · 검색 M건 중 법제처 응답 R건만 일자순 정렬 — 최신순 미보장(더 최신 자료가 목록 밖에 있을 수 있음)
> ```
>
> - 검색에는 **일자 내림차순 정렬(`sort=ddes`)을 요청**합니다. "최신순"이라 적는 것은 **받은 순서가 실제로 일자 내림차순**이거나, **검색 결과를 전부 받았고 일자를 모두 읽어** 받은 목록을 일자순으로 다시 정렬한 경우뿐입니다. 둘 다 아니면 "일자순 … 최신순 미보장"으로 적습니다.
> - 받은 순서가 내림차순이라는 것은 **받은 목록 안의 사실**입니다. 목록 밖까지 최신이라는 것은 법제처가 정렬 요청을 지켰다는 전제에 기댑니다.
> - 검색 총건수(`totalCnt`)가 없거나 숫자가 아니거나 받은 건수보다 작으면, 총건수를 지어내지 않고 `받은 N건(검색 총건수 미확인 — 사유)`로 적습니다. 총건수 확인과 정렬 확인은 따로 판정합니다 — 총건수가 미확인이어도 받은 순서가 내림차순이면 "최신순"일 수 있습니다.
> - `fin_nts_ruling`도 같은 규칙입니다. `fin_article`의 예규 후보(최대 3건)는 다시 정렬하지 않고 **받은 순서를 그대로** 보여 주므로, 받은 순서가 내림차순일 때만 "최신 N건"이라 적고 아니면 "일자순 정렬 미확인"이라 적습니다.

**② 근거 조문의 본문을 가져옵니다** — `fin_article(law="법인세법 시행령", article="제45조")` (발췌)

```text
■ 법인세법 시행령 제45조
제45조(복리후생비의 손금불산입)
  ①법인이 그 임원 또는 직원을 위하여 지출한 복리후생비중 다음 각 호의 어느 하나에 해당하는 비용 외의 비용은 손금에 산입하지 아니한다. …
    8. 그 밖에 임원 또는 직원에게 사회통념상 타당하다고 인정되는 범위에서 지급하는 경조사비 등 제1호부터 제7호까지의 비용과 유사한 비용

■ 모법 위임 근거 (역방향)
[모법] 법인세법 제26조
제26조(과다경비 등의 손금불산입) 다음 각 호의 손비 중 대통령령으로 정하는 바에 따라 과다하거나 부당하다고 인정하는 금액은 … 손금에 산입하지 아니한다.
    2. 복리후생비

■ 법령 정보 — 시행일자 20260227 · 원문: https://www.law.go.kr/%EB%B2%95%EB%A0%B9/%EB%B2%95%EC%9D%B8%EC%84%B8%EB%B2%95%20%EC%8B%9C%ED%96%89%EB%A0%B9/%EC%A0%9C45%EC%A1%B0
■ ⚠ 법령 개정 예정(「법인세법 시행령」 법령 단위 — 이 조문 해당 여부는 부칙·개정문 확인) — 2027-01-01 시행 개정 공포됨(공포 2026-02-27) …
```

> `법령 개정 예정` 줄은 **법령 전체에 공포된 미래 시행 개정**을 알리는 것이지, 조회한 조문이 바뀐다는 뜻이 아닙니다. 그 개정이 이 조문에 닿는지는 해당 개정의 부칙·개정문으로 확인하세요(예: 2026-09-24 실측에서 `법인세법 제26조` 조회에 붙은 2028-01-01 시행 개정은 제21조제2호의 개정이었습니다).

**AI가 이 결과를 쓰면 답에 이런 것을 붙일 수 있습니다.**

- 인용한 예규의 **문서번호·회신일자·원문 링크** — 그대로 복사해 검토서에 넣을 수 있는 형태
- 근거 조문의 **본문·시행일자·원문 링크**, 그리고 그 조문을 위임한 **모법 조문**
- **이미 공포된 미래 시행 개정** 경고 — 지금 맞는 답이 내년에도 맞는지
- 초안을 `fin_verify`에 넣으면 인용이 실존하는지 대조합니다. 다만 그 ✓의 뜻은 좁습니다:
  `※ ✓는 법령·조문 번호가 법제처에 실존한다는 뜻입니다. 항·호·내용의 옳고 그름은 검증하지 않습니다`
- **남는 판단은 사람 몫입니다.** 조문은 "사회통념상 타당하다고 인정되는 범위"까지만 말합니다.
  그 축의금이 그 범위인지, 임직원 경조사비인지 거래처 경조사비(기업업무추진비)인지는 사실관계 판단이고,
  이 서버는 그 판단을 대신하지 않습니다.

### 이 도구가 하는 것 / 하지 않는 것

- **합니다** — 법령명+조문으로 조문 본문·위임 조문·예규 후보를 모아 오고, 인용한 번호가 법제처에 실존하는지·삭제됐는지를 대조하고, 조회하지 못한 부분(부분 실패·절단·현행 기준 대체)을 응답에 적습니다.
- **하지 않습니다** — 사안에 대한 세무 판단을 하지 않습니다. 판단은 근거를 보고 사람이 합니다.
- **보장하지 않습니다** — **답변이 원문과 일치함을 보장하지 않습니다.** `fin_verify`의 ✓는 번호의 실존만 뜻하고 항·호·내용이 맞는지는 보지 않습니다. AI가 조회한 원문을 잘못 읽거나, 조회하지 않은 내용을 덧붙이거나, 아예 조회하지 않고 답하는 경우는 이 서버가 잡지 못합니다. 결론을 쓰기 전에 응답에 실린 원문을 직접 확인하세요.

> 범용 법령 MCP와 다른 점: 세법은 "법률–시행령–시행규칙 3단 + 예규"가 한 세트입니다.
> 이 서버는 그 세트를 알고 묶어서 답합니다. 조문 하나를 물으면 위임 시행령 본문과
> 예규 후보까지 **1회 호출**로 옵니다.

## 도구 (기본 7개 · 옵트인 2개)

옵트인 도구는 환경변수를 켰을 때만 목록에 실립니다 — `FIN_NTS_BODY_ENABLED=true`면 `fin_nts_ruling`, `FIN_TOPIC_ENABLED=true`면 `fin_topic`(실험 기능).

| 도구 | 하는 일 |
|------|------|
| `fin_article` | 조문 + 위임 시행령·시행규칙 **본문** + 예규 후보(조문 제목 키워드 검색) + 별표 + **시행예정 개정 경고**를 1회 응답으로 |
| `fin_law_search` | 법령 검색 → 재무 관련도순 재정렬 (부분매칭 함정 방어 · 폐지/연혁/시행예정 표시 · 주제어→법령 힌트) |
| `fin_ruling_search` | 국세청 예규 + 조세심판원 + 법제처 해석례 + 법원 판례(전 심급)를 한 번에. 검색에 **일자 내림차순(`sort=ddes`)을 요청**하고, 받은 순서가 내림차순이거나 결과를 전부 받아 일자를 모두 읽었을 때만 "최신순"이라 적습니다 (아니면 "일자순 … 최신순 미보장" — [규칙](#예를-들면)). 검색 총건수·표시 건수를 함께 표기하고, 총건수를 확인하지 못하면 받은 건수와 사유를 적습니다 + 전거 서열 표기 |
| `fin_nts_ruling` | 국세청 예규 검색 + 상위 건 **본문**(최대 6,000자, 초과 시 절단 고지) 자동 동봉 (문서번호·회신일자 포함). **`FIN_NTS_BODY_ENABLED=true`일 때만 등록** — 기본(off)에서는 목록이 `fin_ruling_search(domains=["nts"])`와 겹쳐 노출하지 않습니다 |
| `fin_annex` | 별표·서식 목록 + 다운로드 링크 (`kind`: 1=별표·2=서식·3=별지·4=별도·5=부록). `annex_no`를 지정하면 그 별표 파일(HWP·HWPX·PDF)을 내려받아 **본문은 마크다운, 표는 병합 셀 보존을 위해 HTML `<table>`**로 반환 (감가상각 내용연수표·세율표). 번호 없는 별표(목록에 `[별표]`)는 `annex_no` 대신 `keyword`로 지정. 법령뿐 아니라 **고시·훈령의 별표·별지서식**도 (국세청 훈령의 별지 서식 등). 파일 링크가 없거나 다운로드·추출이 실패하면 **원문 링크와 사유를 고지**하고 내용을 지어내지 않습니다 |
| `fin_verify` | 초안의 법령·조문·고시 인용을 실존 검증 — **✓있음/✗없음/⚠판정불가 3값**. 조문 형식으로 제공되는 행정규칙은 **조문 존재까지** 대조. **삭제된 조문은 ✓가 아니라 ⚠(사용 보류)**, 국세청 **기본통칙·집행기준은 법제처 DB 미수록**이라 번호를 검증하지 않고 ⚠ |
| `fin_calc` | 법정 산식 결정형 계산 (임원퇴직금 한도·기업업무추진비 한도·감가상각비·가지급금 인정이자·퇴직소득세) — LLM 산수 배제, 계산 과정·근거 조문 동봉 |
| `fin_ping` | 설치 점검 — 서버 상태 + **법제처에 실제로 검색 1건을 보내** 통신되는지 확인. 실패하면 원인과 다음 조치를 함께. ⚠ 통신 성공이 키가 맞다는 보증은 아닙니다 ([5. 됐는지 확인](#5-됐는지-확인)) |
| `fin_topic` | **실험 기능 — `FIN_TOPIC_ENABLED=true`일 때만 등록.** 업무 주제 13개의 큐레이션 표. [아래 절](#실험-기능-fin_topic-옵트인) 참고 |

### 실험 기능: `fin_topic` (옵트인)

조문 번호를 모를 때 쓰는 **보조 진입** 도구입니다. 자연어 질문을 업무 주제 13개의 **큐레이션 표**(사람이 적어 둔 표)에 어절 단위로 맞춰,
답변 전 확인할 사실 + 근거 조문 후보(`fin_article` 인자 그대로) + 예규 검색어 + 계산기 연결을 돌려줍니다. **판정·계산은 하지 않습니다.**

**v0.1에서는 기본 목록에서 뺐습니다** — 폐기가 아니라 검증이 끝나기 전까지 노출을 보류한 것입니다. 쓰려면 `.env`에 `FIN_TOPIC_ENABLED=true`를 넣고 서버를 다시 시작하세요.
끈 상태에서도 도구 이름으로 직접 호출하면 동작합니다(목록에만 싣지 않습니다).

보류한 이유는 매칭 정확도가 아직 낮기 때문입니다. 표를 만들 때 보지 않은 문장 160개로 **한 번** 잰 결과(2026-09):

| 입력 | 결과 |
|---|---|
| 표 안 주제의 질문 104개 | 1위가 맞는 주제 75개(**72%**) · 주제 0건 24개(23%) · 엉뚱한 주제가 1위 5개(5%) |
| 표 밖 세무·노무 질문 40개 | 주제를 잘못 띄운 **오탐 10개(25%)** |
| 업무 잡담 16개 | 오탐 0개 |

- 13개 주제 밖의 질문은 0건이고, 걸린 말이 다른 쟁점에도 쓰이면 엉뚱한 주제가 뜰 수 있습니다. 응답의 `트리거 ← "질문에서 걸린 어절"` 표시로 왜 떴는지 확인하세요.
- 부정문("이건 경조사비가 아닙니다")을 가리지 못하고, 주제가 맞아도 자금 방향(가지급금/가수금)·대상(임원/직원)처럼 결론이 갈리는 축을 표가 다 담지 못합니다.
- 표의 조문은 실존·조문 제목까지만 실 API로 대조합니다(`TOPICS_VERIFIED_AT`) — 제목이 그대로인 채 한도·요건이 바뀌면 감지하지 못합니다.
- 이 도구를 거쳤을 때 AI의 답이 더 나아지는지는 **아직 측정하지 못했습니다.**

**예시** — `fin_topic(question="직원 결혼 축의금을 회사 돈으로 주면 세금 문제 있나요")`

답을 주는 게 아니라 **답하기 전에 확인할 것**과 **다음 호출 인자**를 줍니다.

```text
■ 주제: 임직원 경조사비 (매칭어: 축의금 ← "축의금을" · …)
확인할 사실 (답변 전 반드시):
  · 받는 사람이 임직원인가 거래처인가 → 복리후생비 vs 기업업무추진비로 갈린다
  · 사규(경조사비 지급규정)에 대상·금액이 정해져 있는가 → 사회통념 판단의 출발점
  · 1건 금액 (거래처인 경우 증빙 기준선인 20만원 초과 여부)
근거 조문 후보 → fin_article 인자 그대로:
  · 법인세법 시행령 제45조 (복리후생비의 손금불산입) — 제1항 8호 — 임원·직원에게 "사회통념상 타당하다고 인정되는 범위에서 지급하는 경조사비"는 손금. 열거된 복리후생비 밖은 손금불산입
    {"law":"법인세법 시행령","article":"제45조"}
  · 법인세법 제25조 (기업업무추진비의 손금불산입) — 거래처 경조사비인 경우 이쪽 — 한도·증빙 규정
    {"law":"법인세법","article":"제25조"}
  · 소득세법 시행규칙 제10조 (비과세소득의 범위) — 제1항 — "사업자가 그 종업원에게 지급한 경조금중 사회통념상 타당하다고 인정되는 범위내의 금액은 이를 지급받은 자의 근로소득으로 보지 아니한다". 소득세법 제12조(비과세소득)에는 경조금 항목이 없다
    {"law":"소득세법 시행규칙","article":"제10조"}
예규 검색어: "경조사비" (fin_ruling_search) — "경조사비" 검색 결과는 경조사비의 손금·근로소득·증빙 쟁점에 모인다 — "축의금"으로 찾으면 건수는 비슷하지만 연금저축 이전 같은 무관한 예규가 섞인다
계산: 해당 없음 — 거래처 경조사비라면 fin_calc 기업업무추진비한도로 회사 전체 한도를 먼저 본다 — is_sme(중소기업 여부)를 확인해 넣는다
이 도구가 판단하지 않는 것:
  · "사회통념상 타당하다고 인정되는 범위"의 금액 — 사규·업계 관행·예규 본문으로 판단한다
```

> 위 블록은 **발췌**입니다 — 실제 응답에는 "큐레이션 표이며 조문 본문은 fin_article로 확인하라"는 고지와 **표의 조문을 실 API로 마지막 대조한 날**이 함께 붙습니다.
> 매칭어는 `트리거 ← "질문에서 걸린 어절"` 형태로 적히고, 같은 말이 다른 쟁점에도 쓰이는 트리거에는 `[약]`·`[맥락]` 표시가 붙습니다 — 어느 말 때문에 이 주제가 떴는지 읽는 쪽이 바로 확인하라는 뜻입니다.

### 기준일 조회 (`basis_date`)

과거 시점 기준으로 검토해야 할 때 (경정청구·세무조사 대응 등) `basis_date`(YYYY-MM-DD)를 지정하면
**그 시점에 시행 중이던 법령**으로 답합니다. `fin_article`·`fin_verify`·`fin_law_search`·`fin_ruling_search`가 지원합니다.
`fin_topic`(옵트인)도 `basis_date`를 받지만 스스로 조회하지는 않고(큐레이션 표입니다), 다음 호출용으로 내주는 `fin_article`·`fin_ruling_search` 인자에 그대로 실어 조문만 그 시점, 예규는 현재가 되는 것을 막습니다.
형식이 맞아도 달력에 없는 날짜(`2024-02-30`·`2023-02-29`·`2026-13-01` 등)는 다섯 도구(`fin_topic`은 켰을 때) 모두 조회 전에 `[INVALID_PARAMETER]`로 거절합니다.

- 법령 계열은 기준일 시점 **시행본**을 먼저 찾아(그 판본의 MST를 해소해) 그 버전의 조문을 반환합니다.
  본문 조회에 넘기는 시행일자는 기준일이 아니라 **해소한 판본의 시행일**입니다 — 법제처는 판본 MST에
  그 판본의 시행일이 아닌 날짜를 붙이면 조문을 돌려주지 않습니다. 시행본을 확정하지 못하면 추측 대신
  `BASIS_DATE_UNRESOLVED`(⚠판정불가)로 알립니다.
- 기준일 **당일에 시행된 판본이 없으면**(= 그날 개정이 없었으면) 그 시점에 시행 중이던 **직전 개정본**으로
  조회하고, 헤더에 `(해당일 시행본 없음 → 직전 개정본 YYYY-MM-DD 시행 기준으로 조회)`라고 적습니다.
  이것은 정상 동작이며 **"그날 시행 중인 법령이 없었다"는 뜻이 아닙니다.**
- `fin_article`의 기준일 조회는 **조문 본문·시행일자에만** 적용됩니다. 위임(법제처 3단비교)과 개정 예정은
  법제처가 현행 기준만 제공하므로 **생략**하고 그 사실을 상단에 적으며, 예규 후보·별표는 `[현행 기준]`으로
  표시해 함께 냅니다. 응답의 원문 링크도 현행본 주소라 `— 기준일 시행본이 아님`을 붙입니다.
- `fin_ruling_search`는 시행일이 아니라 **회신·의결·선고일** 기준입니다. 법제처 기간 검색(`19000101~기준일`)으로
  받고 **받은 일자를 다시 대조**해, 걸러진 건이 있으면 제외 건수를 표기합니다(제외가 생겼다는 것은 법제처가
  기간 조건을 무시한 응답이라는 신호입니다).
- `fin_verify`의 기준일은 **조문까지 인용한 법령**에만 적용됩니다. 행정규칙(고시·훈령·규정)과 법령명만 쓴 인용은
  현행 본문으로 대조하므로 ✓·✗ 대신 **⚠ + `[현행 기준 대조 — 기준일 미적용]`**으로 알립니다.
  현행 DB에 없는 **연혁 법령**은 기준일을 줘도 조문 대조까지 가지 않고 ⚠(환각 아님)로 보고합니다 —
  연혁 법령의 기준일 조문 본문은 `fin_article`로 조회하세요.
- **신구조문 대비**는 같은 조문에 `fin_article`을 두 번 호출해서 봅니다 — 개정 전 시점을 `basis_date`로 한 번(예: `basis_date: "2022-12-31"`), 현행을 `basis_date` 없이 한 번. 두 응답의 조문 본문과 시행일자를 비교하면 됩니다.

## 신뢰 원칙 (이 서버의 존재 이유)

세무 검토에서 최악의 실패는 오답이 아니라 **"조용한 실패"** — 오류가 "0건"으로 위장되어 "그런 예규 없음"이라는 잘못된 단정이 검토서에 실리는 것입니다. 이 서버의 규율:

1. **3값 판정**: "없음(✗ — 정상 조회 후 0건)"과 "판정 불가(⚠)"를 절대 같은 값으로 반환하지 않는다. 네트워크 오류·한도 초과·시간 상한은 전부 ⚠. 다만 ⚠가 모두 조회 실패는 아니다 — 조회는 정상이었지만 ✓·✗로 답할 수 없는 경우(법제처 DB 미수록·기준일 미적용·삭제된 조문의 사용 보류·표기 확인 필요)도 ⚠이고, 사유는 판정 줄마다 적힌다.
2. **근거 동봉**: 예규·판례 목록(`fin_ruling_search`)에는 문서번호(`법인세과-352` 형식)·일자·원문 URL을, 조문 본문(`fin_article`)과 ✓ 판정(`fin_verify`)에는 원문 링크를 붙인다 — 복사해서 바로 인용 가능한 형태로. 법제처 자료를 조회하지 않는 `fin_topic`(옵트인 큐레이션 표)·`fin_calc`(산식 계산)의 응답에는 URL이 없다 — 특히 `fin_topic`은 "출처: 법제처" 문구조차 붙이지 않는다(사람이 적어 둔 표를 원문처럼 읽게 하지 않으려고). 대신 **표의 조문을 실 API로 마지막 대조한 날**을 싣는다.
3. **전거 서열 표기**: 법령 조문 > 판례 > 심판례·유권해석 > 예규(행정해석). 예규를 확정 근거처럼 오용하지 않도록 조문 조회(`fin_article`)와 예규·판례 검색(`fin_ruling_search`) 응답에 명시.
4. **개정 경고**: 이미 공포된 미래 시행 개정을 감지해 경고 ("이 법은 2027-01-01 시행 개정이 공포되어 있음").
5. **골든셋 회귀**: 실제 사고 사례(조문 목 45개 절단, 429가 0건으로 표시 등)가 테스트로 박제되어 있다.
6. **부분 실패 계약**: 묶음 응답의 한 섹션이 실패해도 나머지는 살리고, 실패 사유를 그 자리에 명시한다. 도구 처리 중 예상하지 못한 예외도 오류 응답(`[코드] … ⚠판정불가 (0건이 아님)`)으로 돌려준다 — 프로그래밍 오류는 `INTERNAL_ERROR`로 분류하고, 예외 원문(요청 주소 등)은 응답에 싣지 않는다.

"검증한다"는 말이 무엇을 뜻하는지는 [docs/BENCHMARK.md](./docs/BENCHMARK.md)에 재현 가능한 게이트로 정의해 두었습니다 —
정상 인용 20문장이 전부 ✓로 통과하는지(거짓 양성 차단), 그리고 **실제로 발생했던 오검증·조용한 실패 83건**
(틀린 인용에 ✓ / 맞는 인용에 ✗ / 조용한 누락 — 라운드별 원인과 박제 위치는 문서 3장)이 재발하지 않는지.
83건 중 77건은 테스트로 박제되어 `npm test`가 지키고, 6건(#36·38·48·51·52·69)은 박제 위치가 테스트가 아니라
소스 코드·훅 스크립트·문서로 적혀 있습니다(문서 3장 표의 "박제" 칸). 두 방향 모두 통과해야 합니다.

## 설치

**필요한 것: [Node.js](https://nodejs.org) 20.19.0 이상** (`node -v`로 확인). 그 외 준비물은 없습니다.

### 1. 내려받아 빌드

Windows PowerShell·macOS·Linux 모두 한 줄씩 그대로 입력하면 됩니다.

```bash
git clone https://github.com/dolseom/fin-law-mcp.git
cd fin-law-mcp
npm install
npm run build
```

### 2. 법제처 API 키 발급 (무료)

[법제처 OPEN API 신청](https://open.law.go.kr/LSO/openApi/guideResult.do)에서 가입하면 **가입 이메일의 @ 앞부분이 그대로 키**입니다.
(예: `hong@company.com`으로 가입했다면 키는 `hong`)

### 3. `.env` 파일 만들기

저장소 최상위 폴더(`build/`와 같은 위치)에서 한 줄이면 됩니다. 서버는 실행 위치와 상관없이 이 위치의 `.env`를 읽습니다.
`.env` 대신 AI 등록 설정의 `env`로 키를 넘겨도 됩니다 — 아래 4단계 참고.

```powershell
# Windows PowerShell
Set-Content -Encoding utf8 .env "LAW_OC=발급받은키"
```

```bash
# macOS · Linux
echo 'LAW_OC=발급받은키' > .env
```

### 4. AI에 등록

- **Claude Code**: `claude mcp add fin-law node /절대경로/fin-law-mcp/build/index.js`
- **Claude Desktop**: `claude_desktop_config.json`의 `mcpServers`에 추가

```jsonc
// macOS · Linux
{
  "mcpServers": {
    "fin-law": { "command": "node", "args": ["/절대경로/fin-law-mcp/build/index.js"] }
  }
}
```

```jsonc
// Windows — 경로 구분자를 \\ 로 두 번 쓰거나, / 로 써도 됩니다
{
  "mcpServers": {
    "fin-law": { "command": "node", "args": ["C:\\dev\\fin-law-mcp\\build\\index.js"] }
  }
}
```

**`.env` 파일 없이 등록 설정으로 키를 넘기려면** (3단계를 건너뛴 경우)

- **Claude Code**: `claude mcp add fin-law -e LAW_OC=발급받은키 -- node /절대경로/fin-law-mcp/build/index.js`
- **Claude Desktop**: 서버 항목에 `env`를 추가합니다. 다른 환경변수(아래 [환경변수](#환경변수) 표)도 같은 자리에 넣습니다.

```jsonc
{
  "mcpServers": {
    "fin-law": {
      "command": "node",
      "args": ["/절대경로/fin-law-mcp/build/index.js"],
      "env": { "LAW_OC": "발급받은키" }
    }
  }
}
```

`.env`와 등록 설정에 같은 변수가 모두 있으면 **등록 설정 값이 쓰입니다** — `.env`는 이미 설정된 환경변수를 덮어쓰지 않습니다.
키를 바꿨는데 반영되지 않으면 두 곳을 모두 확인하세요.

### 5. 됐는지 확인

AI에게 **`fin_ping 실행해줘`** 라고 말하세요. 이렇게 나오면 끝입니다.

```text
fin-law-mcp v0.1.0 정상 동작
LAW_OC: 설정됨 · 법제처 API 통신: 성공 (법인세법 검색 1건, 123ms)
  ※ 통신 성공은 키 값이 맞다는 확인이 아닙니다 — 틀린 키에도 법제처가 정상 응답한 실측 사례가 있습니다(원인 미확인). 키는 .env의 LAW_OC를 직접 확인하세요
FIN_NTS_BODY_ENABLED: 미설정(기본 off) — 예규는 목록·링크만. 본문이 필요하면 .env에 true
FIN_TOPIC_ENABLED: 미설정(기본 off) — 실험 기능 fin_topic 미등록
```

위 블록은 **형식 예시**입니다 — 검색 건수와 소요 시간(`123ms`)은 호출할 때마다 달라지는 값이고,
`FIN_NTS_BODY_ENABLED`를 `true`로 두었다면 그 줄이 `true — 국세청 예규 본문 동봉 사용 (fin_nts_ruling 등록됨)`으로,
`FIN_TOPIC_ENABLED`를 `true`로 두었다면 마지막 줄이 `true — 실험 기능 fin_topic(업무 주제 큐레이션 표) 등록됨`으로 나옵니다.

`fin_ping`은 키가 설정됐는지만 보지 않고 **법제처에 검색 1건을 실제로 보내** 통신되는지를 봅니다
(캐시를 읽지 않고 나가므로, 직전 호출이 담아 둔 응답으로 "성공"이 나오지 않습니다. 받은 정상 응답은 캐시에 담깁니다).
`법제처 API 통신: 실패`나 `LAW_OC: 누락`이 나오면 그 줄 아래에 `→ 다음 조치:`로 **원인과 할 일이 함께** 나옵니다.
실패 사유는 다음으로 갈라집니다 — 서로 조치가 다릅니다.

| 나오는 말 | 뜻 | 다음 조치 |
| --- | --- | --- |
| `네트워크 연결 실패` | DNS·연결·TLS 단계에서 끊김 | 인터넷 연결과 사내 프록시·방화벽 확인 (법제처 경로는 `LAW_EXTERNAL_HTTPS_PROXY`를 타지 않습니다) |
| `타임아웃` | 5초 안에 응답 없음 | 브라우저로 https://www.law.go.kr 이 열리는지 확인 |
| `법제처가 빈 응답을 반환` | 200인데 본문이 빔 — 키 거부가 아니라 장애 신호 | 잠시 후 재시도 |
| `HTML 오류 페이지 수신` | 점검 중이거나 접근 차단 | 브라우저로 확인 후 재시도 |
| `응답은 왔으나 법인세법 검색 결과가 0건` | 통신은 됐지만 정상 응답이 아님 | 재시도하고, 계속되면 `LAW_OC` 값 확인 |
| `법제처가 오류 응답을 반환` | 키가 거부됐을 가능성이 큼 | `.env`의 `LAW_OC`가 가입 이메일 @ 앞부분과 같은지 확인 |
| `이 서버의 분당/일일 호출 한도 … 소진` | 법제처 거부가 아니라 **로컬 한도**(`FIN_DRF_RATE_PER_MIN`·`FIN_DRF_DAILY_CAP`) | 안내된 대기 시간 뒤 재시도 — 한도를 더 조이지 마세요 |
| `법제처가 호출 한도 초과(429)를 반환` | 원격 한도 | 1~2분 뒤 재시도, 같은 키를 여러 도구가 쓰면 `FIN_DRF_RATE_PER_MIN`을 낮춤 |
| `법제처 서버 오류 (5xx)` | 법제처 쪽 장애 | 잠시 후 재시도 |

> ⚠ **`통신: 성공`이 키가 맞다는 보증은 아닙니다.** 틀린 키로도 법제처가 정상 데이터를 돌려준 경우가 실측됐습니다(원인은 확인되지 않았습니다).
> 키 오타는 이 진단으로 걸러지지 않을 수 있으니, 2단계 안내대로 **가입 이메일의 @ 앞부분과 한 글자씩 대조**하세요.

### (선택·고급) 설치 용량 줄이기

빌드가 끝난 뒤 별표 추출에 쓰는 `kordoc`의 OCR 옵션 스택(onnxruntime·transformers·sharp)을 걷어냅니다. `fin_annex`는 OCR을 쓰지 않아 별표 표 추출은 그대로 동작합니다 (실측 905MB → 70MB).

```bash
npm prune --omit=optional
```

- 다시 빌드하려면 `npm install`을 한 번 더 실행하세요. prune은 TypeScript 컴파일러 바이너리도 함께 지웁니다.
- ⚠ **처음부터 `npm install --omit=optional`로 건너뛰면 빌드가 깨집니다.** TypeScript 7은 컴파일러 본체를 플랫폼별 `optionalDependencies`(`@typescript/typescript-<플랫폼>`)로 배포해서 `tsc`까지 함께 빠지기 때문입니다.
- `npm audit`은 설치된 트리가 아니라 `package-lock.json`을 읽습니다. prune 후에도 OCR 스택 경유 취약점(sharp→libvips 등)이 같은 건수로 계속 보고됩니다 — 줄지 않는 것이 정상입니다.

| `FIN_NTS_RATE_PER_MIN` / `FIN_NTS_DAILY_CAP` | 국세청 예규 본문 경로(`taxlaw.nts.go.kr`)의 호출 한도 (기본 10/분, 200/일). 법제처 한도와 별도로 셉니다 |
| `FIN_DRF_RATE_PER_MIN` / `FIN_DRF_DAILY_CAP` | 법제처 호출 한도 (기본 30/분, 1,500/일) |
| `FIN_DRF_MAX_CONCURRENCY` | 동시 호출 상한 (기본 4) |
| `FIN_CACHE_TTL_SEC` | 캐시 TTL (기본 600초, `0`·음수·숫자 아닌 값이면 비활성). **응답 본문 캐시와 검색·폐지연혁 파싱 결과 캐시 두 계층을 함께 제어**하고 각 계층 자체 TTL의 상한이 된다 — `0`이면 둘 다 완전히 꺼진다. 같은 조회의 반복 왕복을 프로세스 안에서 접는다 (행정규칙 본문 213~405KB 재조회 1258ms → 9ms) |
| `FIN_CACHE_MAX_ENTRIES` / `FIN_CACHE_MAX_MB` | 캐시 상한 (기본 200건 / 16MB). 상한을 넘으면 오래된 항목부터 버린다 (담지 않는 응답은 [알아둘 것](#알아둘-것)의 캐시 항목 참고) |
| `LAW_API_PROTOCOL` | `http`로 두면 법제처 호출을 평문 http로 보냅니다 (폐쇄망 전용 — 시작 시 경고를 냅니다). 그 밖의 값은 https |
| `LAW_RESPONSE_TYPE` | ⚠ **현재 공개 도구에는 효과가 없습니다 — XML 장애 우회 수단으로 쓸 수 없습니다.** 도구가 쓰는 조회는 응답 형식이 고정돼 있습니다(법령 검색·행정규칙 검색·행정규칙 본문·자치법규 검색은 XML — 파서가 XML 전용이라 JSON을 받으면 정상 응답도 "0건"으로 위장되고 오류 루트 검사까지 꺼집니다 / 3단비교·별표 목록은 JSON / 그 밖의 조회는 호출마다 형식을 지정). 이 변수를 읽는 조회(신구법 비교·조문 연혁·법령 연혁)는 어느 도구도 호출하지 않습니다 |
| `LAW_USER_AGENT` / `LAW_REFERER` | (선택·진단용) 요청 헤더 덮어쓰기. 기본은 일반 브라우저 User-Agent와 `https://www.law.go.kr/` — 법제처는 Node 기본 User-Agent를 거부하고, Referer가 없으면 키가 맞아도 "사용자 정보 검증에 실패" 응답을 줍니다. User-Agent는 이 서버의 외부 요청 전부(사내 프록시 경유 요청 제외)에, Referer는 `law.go.kr` 주소에만 붙습니다. 빈 값이면 기본값을 쓰고, 서버 시작 때 한 번 읽으므로 바꾸면 재시작해야 합니다. 보통은 설정하지 않습니다 |
| `LAW_EXTERNAL_HTTPS_PROXY` | 사내 프록시 경유 (`http://호스트:포트`, 인증은 `http://사용자:암호@호스트:포트`). ⚠ **적용 범위는 국세청 예규 본문 조회(`taxlaw.nts.go.kr`) 한 곳뿐입니다** — 법제처 경로(조문·검색·해석례·별표 파일 다운로드)는 프록시를 타지 않고 직접 나갑니다. 아웃바운드가 프록시로만 열린 망에서는 그쪽이 먼저 실패합니다. **경로 통일은 v0.2 예정** |
| `LAW_EXTERNAL_TLS_REJECT_UNAUTHORIZED` | `0`이면 위 프록시 구간의 TLS 검증을 끕니다 (진단용 임시 우회). `NODE_ENV=production`에서는 무시하고 항상 검증합니다 |

## 알아둘 것

- **국세청 예규 본문**은 국세법령정보시스템의 공식 API가 아닌 내부 경로로 조회합니다. 사이트 개편 시 중단될 수 있으며, 그 경우 목록+원문 링크로 자동 강등됩니다 (조용히 사라지지 않습니다).
- `fin_calc`의 산식에는 **기준 시행일이 명시**됩니다. 세법은 매년 개정되므로 중요한 판단 전에 `fin_article`로 현행 조문과 교차 확인하세요.
- **행정규칙(고시·훈령)의 조문 검증은 규칙에 따라 갈립니다.** 법제처가 조문 형식(`조문형식여부=Y`)으로 제공하는 규칙(「조사사무처리규정」·「법인세 사무처리규정」 등 국세청 훈령 다수)은 본문 조문과 대조해 ✓/✗로 판정합니다. 통짜 본문으로 오는 규칙(「외국환거래규정」 등 — 자체 조문 체계 "제1-1조"를 씁니다)은 "규정은 실존, 제23조는 미확인(⚠)"으로 나옵니다 — ✗(없음)와 구분됩니다.
- **삭제된 조문은 ✓가 아니라 ⚠(사용 보류)입니다.** 법제처는 삭제된 조문도 번호를 남깁니다(`제39조 삭제 <2001.12.31>`). 번호가 남았다고 ✓를 주면 삭제된 조문이 "실존"으로 통과하므로, **조 전체가 삭제된 자리표시**면 `⚠ [사용 보류] 삭제된 조문`으로 보고하고 요약 헤더에도 따로 띄웁니다 — **✗(없음)이 아닙니다.** 삭제 전 규정을 인용한 문서라면 `basis_date`로 그 시점을 지정해 재검증하세요. **항·호 하나만 삭제된 조문은 살아 있는 조문**이라 이 판정을 받지 않습니다. 같은 판정은 `fin_article`에도 적용돼, 삭제 조문에는 위임·예규 후보를 싣지 않고 그 사유를 밝힙니다.
- **국세청 기본통칙·「○○세(법)집행기준」은 법제처 DB에 없습니다.** 이름에 "통칙"이 든 규칙은 법제처 행정규칙 DB에 한 건도 없어(2026-09-16 실측), 0건을 "존재하지 않음"의 증거로 쓸 수 없습니다. 그래서 `fin_verify`는 **번호의 실존을 검증하지 않고** 모법(예: 「법인세법」)의 실존만 확인해 ⚠로 보고합니다 — 원문은 국세법령정보시스템에서 확인하세요. 이 ⚠는 인용이 틀렸다거나 쓰면 안 된다는 뜻이 아니라 **원문 대조가 필요하다**는 뜻입니다(모법까지 확인되지 않으면 그때는 ⚠(사용 보류)). 이름이 "집행기준"으로 끝나더라도 **법제처 DB에 실존하는 규칙**(예: 「(계약예규)정부 입찰ㆍ계약 집행기준」)은 일반 행정규칙으로 정상 대조합니다. 고시·훈령·예규는 종전대로 DB에 없으면 ✗입니다.
- `fin_verify`는 **따옴표(「」) 없이 쓴 "…규정"·"…규칙" 인용**(시행규칙 제외)을 사내 규정·사규일 수 있다고 보고 미발견 시 ✗가 아닌 ⚠(사용 보류)로 답합니다. 법령·고시를 인용한 것이라면 「」로 감싸세요 — 그러면 사내 문서로 보지 않고, 찾지 못하면 ✗로 판정합니다. 다만 「」로 감싸도 **항상 ✗가 되지는 않습니다**: 이름이 비슷한 법령이 검색에 함께 걸리면 ⚠(정확 일치 없음 — 표기 확인 필요), 약칭 형태의 이름이면 ⚠(사용 보류), 폐지·연혁 법령으로 추정되거나 연혁 조회가 실패하면 ⚠로 나옵니다.
- `fin_calc`의 가지급금 인정이자는 **`rate_type`에 기본값이 없습니다.** 법인세법 시행령 §89③ 본문은 가중평균차입이자율이 시가이고 당좌대출이자율은 단서의 예외라, 어느 쪽인지 밝히지 않으면 계산하지 않습니다.
- 같은 이유로 `fin_calc`의 기업업무추진비 한도는 **`is_sme`(중소기업 여부)에 기본값이 없습니다.** 기본한도가 연 1,200만원과 3,600만원(중소기업, 법인세법 §25④1)으로 3배 갈리므로, 밝히지 않으면 계산하지 않습니다. 결과에는 입력한 중소기업 여부와 수입금액이 그대로 다시 표시됩니다.
- **응답 캐시는 신선도를 최대 TTL(기본 10분)만큼 늦춥니다.** 같은 URL의 조회는 그동안 네트워크를 다시 타지 않으므로, 방금 반영된 개정이나 API 일시 오류의 복구를 즉시 보려면 `FIN_CACHE_TTL_SEC=0`으로 끄고 재조회하세요 — 이 값이면 캐시에 담지도 읽지도 않습니다. `fin_ping`의 통신 진단은 이 설정과 무관하게 캐시를 **읽지 않고** 나갑니다(받은 정상 응답은 담습니다).
  캐시에 담지 않는 응답은 **HTTP 오류 응답, 빈 본문, HTML 장애 페이지, `<error>…`·`{"error":…}` 형태의 대표적인 오류 본문**, 그리고 **200으로 왔지만 그 조회의 응답 검사에 걸린 본문**입니다 — 기대한 루트·최상위 키가 아닌 응답, 끝까지 받지 못한 행정규칙 본문, 오류 키가 든 별표 목록 등. 이런 응답은 "0건"이 아니라 확인 실패(⚠)로 알립니다. 같은 URL이라도 더 엄격한 검사를 하는 조회는 캐시된 본문을 자기 검사로 다시 보고, 통과하지 못하면 새로 조회합니다. **정상적인 0건 응답은 캐시됩니다**(조회가 성공한 결과입니다).
  ⚠ 다만 **"200으로 오는 모든 이상 응답이 걸러진다"는 보증은 아닙니다** — 조회마다 검사의 깊이가 다릅니다(예: 기준일 시행본 목록 조회는 빈 본문·HTML만 보고 루트 이름은 확인하지 않고, 별표 목록은 법령·자치법규·행정규칙별 루트 이름까지는 확인하지 않습니다). 같은 이상이 TTL 동안 반복되면 `FIN_CACHE_TTL_SEC=0`으로 끄고 재조회해 구분하세요.
- **한 번에 많은 인용을 검증하면 뒤쪽이 분당 한도에 걸릴 수 있습니다.** `fin_verify`는 호출당 최대 15건을 검증하고, 인용 하나에 법제처 조회가 여러 번 필요합니다. 서로 다른 법령을 가리키는 인용이 많으면 이 서버의 분당 한도(`FIN_DRF_RATE_PER_MIN`, 기본 30회)를 넘겨 뒤쪽 인용이 ⚠(분당 호출 한도 초과 — 없음 아님)로 남습니다 — 서로 다른 법령 20건을 넣은 테스트 입력에서는 11번째 인용부터 그렇게 됐습니다. 그 인용은 잠시 뒤 나눠서 다시 검증하세요.
- 이 도구의 출력은 참고용입니다. **법적 효력이 필요한 판단에는 반드시 국가법령정보센터 원문을 확인하세요.**

## 개발

```bash
npm run typecheck   # 타입 검사 (src + test 전체)
npm run lint:dead   # 쓰이지 않는 파일·의존성 검사 (knip)
npm run build       # npm test 전에 먼저 — 아래 참고
npm test            # 회귀 테스트 (fixture 기반 — 실 API 불필요, CI 상시)
npm run check       # 위 넷을 CI와 같은 순서로 (typecheck → lint:dead → build → test)
npm run test:live   # 라이브 (실 법제처 API 호출 — LAW_OC 필요, 수동)
                    #   · 골든셋 회귀
                    #   · fin_calc 상수 대조 — 세율표·공제표·상각률·이자율·한도를
                    #     조문 원문과 대조한다 (세법 개정으로 상수가 낡으면 실패)
                    #   · fin_topic 표 대조 — 표의 (법령, 조문)이 실존하고 조문 제목이 표와 같은지
                    #     (fin_topic은 옵트인이지만 표 대조는 항상 돈다)

node scripts/gate20.mjs           # 인용 검증 게이트 (정상 인용 20문장 → 전부 ✓)
node scripts/verify-file.mjs 검토서.md   # 문서 하나의 인용을 통째로 검증
```

- `npm test`의 세 파일(`test/tools-list`·`test/ping-diagnostics`·`test/verify-file-hook`)은 **`build/`의 서버와 훅 스크립트를 실행해** 검사합니다. `build/`가 없으면 이 테스트들은 건너뛰고(skip), 오래된 `build/`가 있으면 고치기 전 코드를 검사합니다 — 소스를 고쳤으면 **빌드를 끝낸 뒤** 테스트하세요.
- 라이브 테스트는 파일명 `*-live.test.ts` 규칙으로 기본 스위트에서 빠지고 `test:live`에만 잡힙니다.

## 로드맵 (v0.2)

- **`fin_article`의 행정규칙 조문 본문 반환** — 지금은 고시·훈령의 조문 *존재*까지만 대조합니다(`fin_verify`). 조문 형식으로 오는 규칙은 본문도 그대로 줄 수 있습니다.
- **`fin_verify` 인용 추출기 재구조화** — 정규화(CRLF·줄바꿈·낱말 안 줄바꿈) / 후보 추출 / 해소(조응·괄호·연혁) 3단 분리. 변형을 조합해 추출 개수와 해소 결과를 검사하는 퍼즈 테스트(`test/verify-fuzz.test.ts`)는 이미 `npm test`에서 돕니다.
- **봉인 평가셋 20문항 1회 실행** — 왕복 수·문서번호 표기율·노이즈 건수를 공개 수치로.

> 계획 없음(검토 후 폐기): 별표 사전 파싱 JSON · 기준일 세션 고정 · 검토서용 인용 패키지 · 로컬 인덱스(SQLite FTS5).
> 별표는 `fin_annex`가 런타임에 추출하고, 기준일은 호출마다 명시하는 편이 "헤더는 기준일, 본문은 현행" 류의 조용한 오류를 막습니다.
